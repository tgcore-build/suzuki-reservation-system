AI提案機能 要件定義書

作成日：2026年9月22日　作成者：開発者本人（techmeets Week22〜24 総合演習）

1. プロジェクト概要

1.1 機能名

AI提案機能（予約・顧客管理システムの追加機能）

1.2 背景・目的

「自分にどのサービス・メニューが合うか分からない」というお客様の声に、来店前の時点で応えられていない。お客様が悩みや要望をAIに伝えると、AIがそれに合ったサービスメニューを提案してくれる機能を作ることで、来店前の不安を減らし、メニュー選びをスムーズにする。

本機能は「予約・顧客管理システム 要件定義書」の本体システムとは別に、独立した機能として要件を定義する。

1.3 対象ユーザー

  • 来店客・見込み客：予約前後に自分の悩みや要望を入力し、おすすめメニューの提案を受け取る。
  • 管理者：提案結果の傾向を把握し、接客やメニュー改善の参考にする（将来的な拡張）。

2. 現状分析

2.1 課題

  • お客様は専門知識がないと選べない悩みを抱えたまま来店・予約している。
  • 対応中に毎回ヒアリングして提案しているが、来店前にある程度絞り込めれば、当日の確認時間を短縮でき、お客様も安心して来店できる。

2.2 現状使用しているツール

  • 現状、メニュー提案を支援するツールは存在しない（すべて対面でのヒアリングに依存）。

3. システム概要

3.1 全体像

お客様がWeb上のチャット画面で悩みや要望を入力すると、AIが質問を重ねながら内容を絞り込み、最終的におすすめのサービスメニューを提案する。バックエンドからAI（LLM）にAPIリクエストを送り、応答を受け取ってチャット画面に表示する、という一往復＋会話履歴の管理で構成する。

3.2 主要機能一覧

  1. チャット形式の悩み・要望入力画面
  2. AIとの会話（複数ターンでのやり取り、絞り込み）
  3. 会話履歴に基づくおすすめメニューの提案
  4. 提案結果の表示（メニュー名・簡単な理由）

4. ユーザーストーリー

「【誰が】として、【何を】したい。なぜなら【なぜ】だから。」の形で、主要機能をユーザーストーリーに落とし込む。

  1. 見込み客として、チャットで自分の悩みや要望を入力したい。なぜなら、来店前にどのメニューが合うか知りたいから。
  2. 見込み客として、AIに質問を重ねてもらいながら悩みを絞り込みたい。なぜなら、専門知識がなくても的確な提案を受けたいから。
  3. 見込み客として、AIからおすすめメニューとその理由を提示してもらいたい。なぜなら、納得したうえでメニューを選びたいから。
  4. 見込み客として、AIの提案結果をそのまま予約に進めたい。なぜなら、提案から予約までをスムーズに完了したいから（顧客向けオンライン予約のメニュー選択画面に、提案されたメニューを選択済みの状態で引き継ぐ）。
  5. 管理者として、AI提案の結果傾向を確認したい（Could have）。なぜなら、接客やメニュー改善の参考にしたいから。

注記： 本機能単体でのユーザーストーリーは5個。プロジェクト全体（本体システムと合わせて）では最低10個の基準を満たしている（本体システム側で12個）。

5. 機能要件（MoSCoW分析）

優先度 機能 詳細
Must have チャットUI お客様がテキストを入力し、AIとやり取りできる画面
Must have AI API連携 入力内容をAI（LLM API）に送信し、応答を受け取る
Must have メニュー提案 会話の内容をもとに、登録済みのサービスメニューの中からおすすめを提示する
Should have 会話履歴の保持 1回のセッション内で、それまでのやり取りを踏まえて質問・提案する（状態管理）
Could have 提案結果の保存 提案結果を顧客情報と紐づけて保存し、来店時に管理者が確認できるようにする
Won’t have 提案結果からの自動予約 今回のスコープ外（提案後は手動で予約フォームへ誘導する）

注記： チャット形式（複数ターンで会話しながら絞り込む形）は、1回の入力で完結するフォーム形式に比べて、会話履歴の管理が必要な分、実装がやや複雑になる。予約・顧客管理システム本体（顧客管理・対応記録・予約・リマインド・既存ソフト連携）を優先して完成させたうえで着手する。

6. 非機能要件

■ パフォーマンス ・AI応答時間：5秒以内を目安とする ・同時接続数：数ユーザー程度（個人店舗規模の運用を想定） ・入力文字数：1メッセージあたり500文字以内を目安とする

■ セキュリティ ・通信はHTTPS化 ・入力内容に個人情報が含まれる可能性があるため、AI APIへの送信内容・保存内容は必要最小限にとどめる

■ 可用性 ・稼働率：予約・顧客管理システム本体に準ずる ・AI API側で障害が発生した場合はエラーメッセージを表示し、通常のヒアリング（対面）に切り替えられるようにする

■ 互換性 ・対応ブラウザ：Chrome、Safari、Edge最新版 ・レスポンシブ対応（スマホ中心）

■ 保守性 ・利用するAI APIの仕様変更に対応できるよう、連携部分を疎結合に保つ ・利用量に応じた従量課金となるため、コスト状況を定期的に確認できるようにする ・専門知識がないお客様でも直感的に使えるよう、質問文はシンプルな言葉で用意する

8. 制約条件

  • 開発期間：予約・顧客管理システム本体（Must have）の完成後に着手。ただし後述の通り、Week22〜24（3週間）では実装を見送り、フェーズ2（Week24以降）で着手する
  • 開発体制：開発者本人による開発（techmeets総合演習）
  • 技術スタック：PHP / Laravel（バックエンド）、外部AI API（LLM）との連携
  • 3週間全体のスケジュールの中で、時間が不足する場合はCould have（提案結果の保存）から先に調整する

スコープの再確認（講師フィードバックを受けて）： 予約・顧客管理システムとAI提案機能を合わせた当初の見積もり工数が3週間に対して過大との指摘を受けた。そのため、Week22〜24ではMust have機能＋顧客向けオンライン予約（空き状況カレンダー優先）を優先して「動くところまで」完成させることとし、AI提案機能はこの3週間では実装せず、設計（本ドキュメント・Week19設計書）を確定させた状態でフェーズ2（Week24以降）に先送りする。

9. 前提条件・リスク

リスク 内容 対応方針
実装難易度 チャット形式は会話履歴の管理（状態管理）が必要で、Week5レベルの単純なAPI呼び出しより一段階複雑 フェーズ2着手時に、まずシンプルな1往復のやり取りで最小実装し、動作確認できてから複数ターンの会話に拡張する2段階アプローチを取る
