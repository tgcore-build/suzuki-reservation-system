Week19 設計書：予約・顧客管理システム（画面設計・DB設計・API設計）

作成日：2026年9月23日　対象：予約・顧客管理システム

この設計書は「予約・顧客管理システム 要件定義書」をもとに、画面設計・DB設計・API設計をまとめたもの。AI提案機能は別紙「Week19 設計書：AI提案機能」で扱う。

Figmaワイヤーフレーム： こちらのリンクから確認できます（左側のページ一覧の「予約システム」ページに本システムの8画面、「AI提案機能」ページにAI提案機能の5画面があります）

連携方針： 本システムはAI提案機能を一切参照しない、単独で完結する設計にする。AI提案機能側からのみcustomer_idで緩く参照される（詳細は別紙参照）。

2. DB設計

2.1 エンティティ一覧

  • admins（管理者）
  • customers（顧客）
  • records（対応記録）
  • menus（メニュー）
  • reservations（予約）
  • reminder_logs（リマインド送信ログ）
  • external_sync_logs（既存ソフト連携ログ）
  • business_hours（営業時間・定休日設定）

2.2 テーブル定義（全テーブル）

テーブル: admins（管理者）

カラム名 型 NULL デフォルト 説明
id BIGINT NO AUTO 管理者ID（PK）
email VARCHAR(100) NO - ログイン用メールアドレス
password VARCHAR(255) NO - パスワード（ハッシュ）
created_at / updated_at TIMESTAMP NO CURRENT 作成・更新日時

【インデックス】PRIMARY KEY (id) ／ UNIQUE KEY (email) 【制約】email: UNIQUE制約／password: 最低8文字

テーブル: customers（顧客）

カラム名 型 NULL デフォルト 説明
id BIGINT NO AUTO 顧客ID（PK）
name VARCHAR(50) NO - 氏名
phone VARCHAR(20) NO - 電話番号
line_id VARCHAR(100) YES NULL メッセージ配信連携用ID
external_id VARCHAR(100) YES NULL 既存ソフト側のID（連携用）
created_at / updated_at TIMESTAMP NO CURRENT 作成・更新日時

【インデックス】PRIMARY KEY (id) ／ INDEX (phone) ／ INDEX (external_id) 【制約】phone: 必須

テーブル: records（対応記録）

カラム名 型 NULL デフォルト 説明
id BIGINT NO AUTO 対応記録ID（PK）
customer_id BIGINT NO - 顧客ID（FK）
reservation_id BIGINT YES NULL 予約ID（FK、紐づく予約がある場合）
menu VARCHAR(100) NO - 提供内容
materials TEXT YES NULL 使用資材
duration_minutes INT YES NULL 対応時間（分）
memo TEXT YES NULL メモ
photo_before VARCHAR(255) YES NULL 前写真パス
photo_after VARCHAR(255) YES NULL 後写真パス
created_at / updated_at TIMESTAMP NO CURRENT 作成・更新日時

【インデックス】PRIMARY KEY (id) ／ INDEX (customer_id) ／ INDEX (reservation_id) 【外部キー】customer_id REFERENCES customers(id) ON DELETE CASCADE ／ reservation_id REFERENCES reservations(id) ON DELETE SET NULL

テーブル: menus（メニュー）

カラム名 型 NULL デフォルト 説明
id BIGINT NO AUTO メニューID（PK）
name VARCHAR(100) NO - メニュー名
price INT NO - 料金（円）
duration_minutes INT NO - 施術時間目安（分）
is_active BOOLEAN NO true 予約画面に表示するかどうか
created_at / updated_at TIMESTAMP NO CURRENT 作成・更新日時

【インデックス】PRIMARY KEY (id) ／ INDEX (is_active)

テーブル: reservations（予約）

カラム名 型 NULL デフォルト 説明
id BIGINT NO AUTO 予約ID（PK）
customer_id BIGINT NO - 顧客ID（FK）
menu_id BIGINT NO - メニューID（FK）
scheduled_at DATETIME NO - 予約日時
source ENUM NO ‘admin’ 予約経路：admin（管理者登録）／online（顧客オンライン予約）
notes TEXT YES NULL 顧客からのご要望（オンライン予約時の自由記述、任意）
status ENUM NO ‘confirmed’ 予約済／完了／キャンセル
created_at / updated_at TIMESTAMP NO CURRENT 作成・更新日時

【インデックス】PRIMARY KEY (id) ／ INDEX (customer_id) ／ INDEX (menu_id) ／ INDEX (scheduled_at) 【外部キー】customer_id REFERENCES customers(id) ON DELETE CASCADE ／ menu_id REFERENCES menus(id) ON DELETE RESTRICT

テーブル: business_hours（営業時間・定休日設定）

カラム名 型 NULL デフォルト 説明
id BIGINT NO AUTO ID（PK）
day_of_week TINYINT NO - 曜日（0=日〜6=土）
open_time TIME YES NULL 開始時刻（定休日はNULL）
close_time TIME YES NULL 終了時刻（定休日はNULL）
is_closed BOOLEAN NO false 定休日フラグ

【インデックス】PRIMARY KEY (id) ／ UNIQUE KEY (day_of_week)

MVP（Week22〜24）では曜日ごとの固定の営業時間・定休日のみ管理する。祝日や臨時休業などの個別対応はCould have（将来拡張）とする。空き状況は「business_hoursの営業時間」から「reservationsの予約済み時間」を差し引いて計算する。

テーブル: reminder_logs（リマインド送信ログ）

カラム名 型 NULL デフォルト 説明
id BIGINT NO AUTO ログID（PK）
reservation_id BIGINT NO - 予約ID（FK）
sent_at DATETIME YES NULL 送信日時（未送信はNULL）
status ENUM NO ‘scheduled’ 送信済／失敗／送信予定

【インデックス】PRIMARY KEY (id) ／ INDEX (reservation_id) 【外部キー】reservation_id REFERENCES reservations(id) ON DELETE CASCADE

テーブル: external_sync_logs（既存ソフト連携ログ）

カラム名 型 NULL デフォルト 説明
id BIGINT NO AUTO ログID（PK）
synced_at DATETIME NO - 取込実行日時
result ENUM NO - 成功／失敗
detail TEXT YES NULL 取込件数・エラー内容など

【インデックス】PRIMARY KEY (id)

2.3 ER図

テキスト形式のER図

customers (1) ----< (N) reservations
customers (1) ----< (N) records
menus     (1) ----< (N) reservations
reservations (1) ----< (0..1) records
reservations (1) ----< (N) reminder_logs

admins・external_sync_logs・business_hoursは、他テーブルと外部キーで結びつかない独立したテーブル（business_hoursは空き状況の計算時にreservationsと突き合わせて使う設定テーブル）。

メソッド エンドポイント 概要

GET /api/booking/availability 指定メニュー・期間の空き状況取得（ログイン不要）
POST /api/booking/reservations 顧客自身による予約の新規作成（ログイン不要）

3.3 API詳細仕様（代表例）

API: 予約一覧取得

【エンドポイント】
GET /api/reservations

【説明】
予約の一覧を取得します。

【認証】
必要（管理者、Bearer Token）

【クエリパラメータ】
- page (integer, optional): ページ番号（デフォルト: 1）
- per_page (integer, optional): 1ページあたりの件数（デフォルト: 20、最大: 100）
- date (string, optional): 絞り込み日付（YYYY-MM-DD）

【レスポンス例（200 OK）】
{
  "data": [
    {
      "id": 123,
      "customer": { "id": 45, "name": "顧客A" },
      "scheduled_at": "2026-10-01T10:00:00+09:00",
      "menu": "メニューA",
      "status": "confirmed"
    }
  ],
  "meta": { "current_page": 1, "total": 32, "per_page": 20 }
}

API: 予約新規登録

【エンドポイント】
POST /api/reservations

【説明】
新しい予約を登録します。

【認証】
必要（管理者、Bearer Token）

【リクエストボディ】
{
  "customer_id": 45,
  "menu_id": 3,
  "scheduled_at": "2026-10-01T10:00:00+09:00"
}

【バリデーション】
- customer_id: 必須、存在するcustomerのID
- menu_id: 必須、存在するmenuのID
- scheduled_at: 必須、未来日時

【レスポンス例（201 Created）】
{
  "id": 123,
  "customer_id": 45,
  "menu_id": 3,
  "scheduled_at": "2026-10-01T10:00:00+09:00",
  "source": "admin",
  "status": "confirmed"
}

【エラーレスポンス例（422 Unprocessable Entity）】
{
  "message": "入力内容に誤りがあります",
  "errors": {
    "scheduled_at": ["予約日時は必須です"]
  }
}

API: 空き状況取得（顧客向け）

【エンドポイント】
GET /api/booking/availability

【説明】
指定したメニューについて、期間内の日時ごとの予約可否（◎予約可／×満席／−営業時間外）を返します。business_hoursの営業時間から、reservationsの予約済み枠を差し引いて計算します。

【認証】
不要

【クエリパラメータ】
- menu_id (integer, required): 対象メニューID
- date_from (string, required): 取得開始日（YYYY-MM-DD）
- date_to (string, required): 取得終了日（YYYY-MM-DD、最大7日分）

【レスポンス例（200 OK）】
{
  "menu_id": 3,
  "slots": [
    { "datetime": "2026-09-26T10:00:00+09:00", "available": true },
    { "datetime": "2026-09-26T10:30:00+09:00", "available": true },
    { "datetime": "2026-09-26T11:00:00+09:00", "available": false }
  ]
}

【エラーレスポンス例（422 Unprocessable Entity）】
{
  "message": "入力内容に誤りがあります",
  "errors": {
    "menu_id": ["メニューを選択してください"]
  }
}

API: 顧客自身による予約作成

【エンドポイント】
POST /api/booking/reservations

【説明】
顧客自身がメニュー・日時・お客様情報を送信し、予約を確定します。ログイン不要。電話番号が既存のcustomersレコードと一致すればそのレコードを使い、一致しなければ新規にcustomersレコードを作成してから予約に紐づけます。

【認証】
不要

【リクエストボディ】
{
  "name": "山田太郎",
  "phone": "090-1234-5678",
  "menu_id": 3,
  "scheduled_at": "2026-09-26T10:00:00+09:00",
  "is_first_visit": true,
  "notes": "前回より少し短めにしたいです",
  "agreed_to_notice": true
}

【バリデーション】
- name: 必須、1-50文字
- phone: 必須、電話番号形式
- menu_id: 必須、存在するmenuのID
- scheduled_at: 必須、未来日時かつ空き状況が「予約可」であること（二重予約防止）
- notes: 任意、200文字以内
- agreed_to_notice: 必須、true であること（注意事項への同意チェック）

見積もりには必ずバッファを乗せる。想定外のバグ修正・仕様変更・レビューやテストの時間は必ず発生するため、開発工数の20〜30%を上乗せして現実的なスケジュールにする。既存ソフト連携と空き状況カレンダーは特に工数が読みにくいため、実際にはこの見積もりよりさらに幅を持たせておく。

注記： 顧客向けオンライン予約はShould haveのため、Must have機能（顧客管理・対応記録・予約管理・管理画面ログイン・自動リマインド・既存ソフト連携）を優先して完成させる。その中でも空き状況カレンダー（自動計算）は顧客体験に直結するため優先的に実装し、時間が不足する場合は顧客向け利用履歴ページ・顧客ログインを後回しにする。

4.2 スケジュール（3週間・3段階）

Week22（基盤）：環境構築・管理者ログイン・顧客管理・予約管理の基本CRUD
  → マイルストーン：管理者が顧客と予約を登録できる

Week23（肉付け）：対応記録（写真添付）・自動リマインド・既存ソフト連携
  → マイルストーン：Must have機能がすべて動く

Week24（仕上げ）：顧客向けオンライン予約（空き状況カレンダー・メニュー選択を優先実装）・バグ修正・デプロイ・README
  → マイルストーン：本番公開・成果物共有

既存ソフト連携は「かかる時間が読めない」リスクが最も高いため、Week23の前半に着手し、想定より時間がかかった場合はWeek24の顧客向け利用履歴ページ・顧客ログイン（Should〜Could have）を削って調整する。空き状況カレンダーを含む顧客向けオンライン予約は優先度が高いため、できる限り残す。

スコープの再確認（講師フィードバックを受けて）： 当初の見積もり合計（予約システム＋AI提案機能）は3週間に対して工数が過大との指摘を受け、Week22〜24で実装する範囲をMust have機能＋顧客向けオンライン予約（空き状況カレンダー優先）に絞り込んだ。AI提案機能は設計まで完了させたうえで、実装はフェーズ2（Week24以降）に先送りする。詳細は「AI提案機能 要件定義書」8. 制約条件を参照。
