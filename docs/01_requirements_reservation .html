予約・顧客管理システム 要件定義書

作成日：2026年9月22日　作成者：開発者本人（techmeets Week22〜24 総合演習）

1. プロジェクト概要

1.1 プロジェクト名

予約制サービス業向け 予約・顧客管理システム（対応記録・リマインドつき）

1.2 背景・目的

本プロジェクトの対象は、予約制でサービスを提供する店舗である。予約管理や顧客ごとの対応記録（過去の利用内容・使用した資材・対応時間・メモ）は既存の予約管理ソフトで一部管理しているが、リマインド送信や利用履歴の顧客への公開など、既存ソフトだけではカバーしきれない部分がある。

本プロジェクトは、techmeetsカリキュラムWeek22〜24（3週間の総合演習）の集大成として、実際の店舗業務で使う予約・顧客管理の基幹システムを自分の手で開発することを目的とする。

1.3 対象ユーザー

  • 管理者：唯一の管理者ユーザー。顧客管理・対応記録・予約管理を行う。
  • 来店客：リマインドを受け取る。メニューと空き日時を選んでオンラインで予約する。将来的には自分の利用履歴の閲覧も想定。

2. 現状分析

2.1 現状の業務フロー

  • 予約・顧客情報の一部は既存の予約管理ソフトで管理している。
  • 対応前後の写真や細かい対応メモは、既存ソフト側で十分に管理しきれていない（今回のシステムで補う想定）。
  • 来店リマインドは現状、手動または未実施。自動リマインドがない。
  • 顧客が自分の利用履歴を見る手段がない。

2.2 課題

  • 次回来店を忘れるお客様がいる → リマインドがないため機会損失につながっている。
  • 対応記録（内容・使用資材・対応時間・メモ・写真）を一元管理できていない。

2.3 現状使用しているツール

  • 既存の予約管理ソフト：API提供状況・データエクスポート可否は現時点で未確認。Week22序盤の最優先調査事項とする。

3. システム概要

3.1 全体像

Laravel（PHP）+ MySQL + Dockerで構築するWebアプリケーション。管理者が管理画面から顧客・対応記録・予約を管理し、来店予定の一定日数前になると自動でリマインドが送信される。将来的にはお客様自身が利用履歴を見られるページを公開する。

3.2 主要機能一覧

  1. 顧客管理（顧客マスタ）
  2. 対応記録（提供内容・使用資材・対応時間・メモ・前後の写真添付）
  3. 予約管理（一覧・作成・編集）
  4. 管理画面ログイン
  5. 自動リマインド送信（来店予定の一定日数前に送信）
  6. 既存予約管理ソフトとのデータ連携（自動取り込み）
  7. 顧客向け利用履歴ページ（簡易ログイン）
  8. 顧客向けオンライン予約（メニュー選択・空き日時カレンダー・お客様情報入力による自己予約）

4. ユーザーストーリー

「【誰が】として、【何を】したい。なぜなら【なぜ】だから。」の形で、主要機能をユーザーストーリーに落とし込む。

  1. 管理者として、顧客情報を登録・編集したい。なぜなら、来店するお客様の情報を一元管理し、対応履歴を紐づけて管理したいから。
  2. 管理者として、顧客を名前や電話番号で検索したい。なぜなら、多くの顧客の中から目的の顧客をすぐに見つけたいから。
  3. 管理者として、顧客ごとの対応記録（メニュー・使用資材・対応時間・メモ・写真）を残したい。なぜなら、次回の対応時に過去の内容を正確に振り返りたいから。
  4. 管理者として、予約を登録・編集・キャンセルしたい。なぜなら、日々の予約状況を正確に把握し、ダブルブッキングを防ぎたいから。
  5. 管理者として、ダッシュボードで本日の予約を一目で確認したい。なぜなら、当日の準備をスムーズに行いたいから。
  6. 管理者として、管理画面にログインしたい。なぜなら、顧客の個人情報を第三者に見られないようにしたいから。
  7. 管理者として、来店予定の一定日数前にお客様へ自動でリマインドを送信したい。なぜなら、来店忘れによる機会損失を減らしたいから。
  8. 管理者として、リマインドの送信状況（送信済み・送信予定・失敗）を確認したい。なぜなら、送信漏れやエラーにすぐ気づきたいから。
  9. 管理者として、既存の予約管理ソフトのデータを自動で取り込みたい。なぜなら、同じ顧客情報を二重に入力する手間をなくしたいから。
  10. 顧客として、来店前にリマインドを受け取りたい。なぜなら、予約を忘れずに来店したいから。
  11. 顧客として、簡単な方法でログインして自分専用のページを見たい。なぜなら、複雑な会員登録なしで気軽に使いたいから。
  12. 顧客として、自分の過去の利用履歴を確認したい。なぜなら、前回どんな内容だったかを来店前に思い出したいから。
  13. 顧客として、メニューと空いている日時を自分で選んで予約したい。なぜなら、電話や来店を待たずに好きなタイミングで予約を完結させたいから。
  14. 顧客として、予約する前に空き状況を確認したい。なぜなら、埋まっている時間帯を何度も問い合わせずに済ませたいから。

5. 機能要件（MoSCoW分析）

優先度 機能 詳細
Must have 顧客管理 顧客マスタ（氏名・連絡先等）のCRUD
Must have 対応記録 提供内容・使用資材・対応時間・メモ・前後の写真添付を記録・閲覧
Must have 予約管理 予約の一覧表示・新規作成・編集
Must have 管理画面ログイン 管理者専用の認証つき管理画面
Must have 自動リマインド メッセージ配信APIを用いて、来店予定の一定日数前に自動でリマインドメッセージを送信
Must have 既存ソフト連携 既存の予約管理ソフトのデータを自動で取り込む（API連携 or CSV取り込み。方式はWeek22序盤の調査結果次第）
Should have 顧客向けオンライン予約 お客様がメニューと空き日時を自分で選び、情報を入力してその場で予約を確定できる機能
Should〜Could have 顧客向け利用履歴ページ 簡易ログインで自分の利用履歴を閲覧できるページ
Won’t have オンライン決済 今回のスコープ外
Won’t have 複数店舗・複数スタッフ対応 今回のスコープ外
Won’t have 予約時アンケートのカスタム設定・メールマガジン配信 店舗ごとに質問内容を設定する仕組みは開発規模を超えるため、自由記述の「ご要望」欄1つで代用する
Won’t have AI提案機能 別紙「AI提案機能 要件定義書」を参照

注記： 自動リマインドと既存ソフト連携は、当初技術的難易度の高さ（API調査未了・Webhook設定の複雑さ）を理由に「今回は見送り」を提案したが、最終的に両方ともMust haveとして正式に採用。既存ソフト連携は、そのAPI・エクスポート対応状況が未確認のため、Week22序盤に必ず仕様確認を行うことをリスク対応として明記する。

顧客向けオンライン予約は、外部の予約サイト（既存ソフト側）の画面を参考に追加した機能。Must have（顧客管理・対応記録・予約管理・管理画面ログイン・自動リマインド・既存ソフト連携）を優先して完成させたうえで着手する。その中でも空き状況カレンダー（自動計算）は顧客体験に直結するため優先的に実装し、時間が不足する場合は顧客向け利用履歴ページ・顧客ログインなど他のShould〜Could have機能を先に後回しにする。

6. 非機能要件

■ パフォーマンス ・ページ読み込み時間：3秒以内 ・同時接続数：10ユーザー程度（個人店舗規模の運用を想定） ・画像アップロード：対応記録の前後写真は1枚あたり5MB以内

■ セキュリティ ・通信はHTTPS化 ・パスワードはハッシュ化して保存 ・管理画面はログイン必須とし、顧客の個人情報へのアクセスを制限する ・XSS、CSRF対策を実施

■ 可用性 ・稼働率：目標99%以上（個人運用のため完全な保証はしない） ・定期メンテナンス：月1回程度、深夜帯に実施 ・自宅サーバーではなく、Render・Railwayなど外部ホスティングへのデプロイを想定（Week24で対応）

■ 互換性 ・対応ブラウザ：Chrome、Safari、Edge最新版 ・レスポンシブ対応（顧客はスマホ中心、管理者はPC・タブレットも想定）

■ 保守性 ・開発者本人が今後も保守する前提で、ドキュメントを整備する ・Laravelの標準的なコーディング規約・MVC構成に準拠する ・主要機能（予約登録・リマインド送信等）にはテストコードを作成する

8. 制約条件

  • 開発期間：Week22〜24の3週間
  • 開発体制：開発者本人による開発（techmeets総合演習）
  • 技術スタック：PHP / Laravel / MySQL / Docker（バックエンド）、Blade / Tailwind CSS / Alpine.js（フロントエンド）、Render・Railway（デプロイ先候補）
  • 学習中の技術（Tailwind CSS・Alpine.jsなど）を含むため、実装に慣れが必要な期間を見込む

9. 前提条件・リスク

リスク 内容 対応方針
既存ソフト連携の実現可否 既存ソフト側がAPIやCSVエクスポートに対応しているか未確認 Week22序盤に最優先で仕様確認。対応していない場合は手動CSV取り込み等の代替案を検討
メッセージ配信APIの設定 公式アカウント開設・Webhook設定など、Week5のAPI学習より一段階複雑 Week22中に先行して公式アカウントを開設し、最小構成（1通送るだけ）から動作確認する
3週間という期間の妥当性 Must have機能だけでも「既存ソフト連携」「自動リマインド」という技術的難易度の高い機能が含まれ、スケジュールがタイトになる可能性がある スケジュールが遅れそうな場合は、Should〜Could have（顧客向けオンライン予約・利用履歴ページ）から先に調整する
顧客向けオンライン予約の複雑さ 空き状況をリアルタイムに計算する仕組みは、単純なCRUDより一段階複雑 空き状況カレンダーを優先実装のうえで着手する。時間が不足する場合は、顧客向け利用履歴ページ・顧客ログインなど他のShould〜Could have機能を先に調整する
