2. 選定理由

PHP / Laravel

techmeetsカリキュラムで学習してきた言語・フレームワークであり、Week22時点で最も使い慣れている。認証・CRUD・バリデーションといった本プロジェクトの中心機能が標準機能として揃っており、MVC構成に沿って開発できるため、3週間という短い期間で個人開発するのに適している。

比較検討： Node.js（Express）やPython（Django）も選択肢としてはあり得るが、いずれも新たに学習し直すコストが発生し、今回の期間には見合わないため不採用とした。

MySQL

Laravelとの親和性が高く、顧客・予約・対応記録・メニューのようにリレーション（紐付け）を持つデータを扱うのに適している。個人店舗規模（同時接続10ユーザー程度）の運用であれば性能面でも十分。

Docker

開発環境をコードとして再現できるため、環境構築の手間や「自分のPCでは動くが本番では動かない」という事態を避けられる。本番環境（Render・Railway）へのデプロイ時も、環境差異を最小限にできる。

Blade

Laravel標準のテンプレートエンジンであり、追加の学習コストなしに利用できる。

比較検討： Vue.jsやReactを使ったSPA構成も検討したが、学習コストと開発工数（状態管理・ビルド環境の構築など）が本プロジェクトの規模に対して過大であり、個人開発かつ3週間という制約に合わないため不採用とした。

Tailwind CSS

ユーティリティクラスを組み合わせるだけで、レスポンシブなUIを手早く組める。CSSを1から設計するデザイン専任者がいない個人開発において、実装スピードを優先できる。

Alpine.js

顧客向けオンライン予約の空き状況カレンダーや、AI提案チャットの会話ログ表示など、ページ遷移を伴わない軽量な動的UIが必要な箇所がある。フル機能のSPAフレームワークを導入するほどの複雑さはなく、Bladeとの組み合わせで必要十分な対話性を実現できるため採用した。

外部AI API（LLM）

自前でAIモデルを学習・運用するのは今回の期間・規模では非現実的。既存のLLM提供APIを組み合わせることで、チャット形式のメニュー提案を3週間の後半（Sprint3）という限られた時間内でも実装できる。利用料は従量課金となるため、コスト状況を定期的に確認する運用とする（要件定義書 6. 非機能要件を参照）。

Render / Railway

個人開発・小規模運用に見合った料金体系と、デプロイの手軽さを重視して選定した。自宅サーバーやVPSを自分で運用・保守する場合と比べて、セキュリティパッチ適用やサーバーダウン対応などの保守負担を減らせる。

Git / GitHub

バージョン管理はもちろん、Week21課題の提出方法（リポジトリ・README・docsフォルダ・Issues）そのものがGitHubの利用を前提としているため。

3. まだ学んでいない技術の扱い

Tailwind CSSとAlpine.jsは、要件定義・設計の時点では使用技術として決定しているが、実装方法の詳細はWeek23で本格的に学ぶ。Week22の時点では「このプロジェクトではこの技術を使う」という前提で設計を進めている。Render・Railwayへのデプロイも同様に、実践としてはWeek24で扱う。
